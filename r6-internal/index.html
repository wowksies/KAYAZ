what it is

Omnis R6 Internal is the internal version of Omnis for Rainbow Six Siege. The R6 External reads everything from outside the game, but this one runs inside it, so it has direct access to the game's data.

It works with BattlEye running and on all QB's. Right now the focus is visuals: health, box and skeleton ESP on every player, and chams are being worked on next.

How the internal works — camera to skeleton

deep dive: how the internal actually works — the writeup that lives with the code

Written 2026-09-24, when the internal was working end to end: camera, boxes that move every frame, health bars, dead check, and skeletons on every operator in a real match. Last updated 2026-09-27: own overlay window instead of the DX12 hook (§7), the binding fix for crowded scenes (§6.5), aimbot and menu written up (§8, §9).

Everything here was measured on build TimeDateStamp 0xAD164C52 / SizeOfImage 0x1CDAB000 (main account). Addresses and offsets change per build and per account — this file explains how each value is found, so it can be found again. Numbers are given as "this build" examples.

Links are relative to this file (try\). Archived code lives one level up in ../_archive/.

Startup order matters: the overlay starts first and its first drawn frame is the signal that R6 is past startup; only then do the scans begin (scanning while R6 is still paging in / compiling shaders hit uncommitted pages and crashed uncatchably). The legacy GetGameState thread (EntityCache's old round-state system) is off (STAGE3_MASK = 6 in dllmain) — every early crash died in its signature sweep and the ESP needs nothing from it.

1. Build, inject, logs, eject

  • Build only Dominate.vcxproj /p:Configuration=Internal /p:Platform=x64 (PowerShell MSBuild). Release|x64 is the external — never build it. Output: build\Omnis_R6.dll. Pipe MSBuild to a file, never to Select-Object -First (that orphans cl.exe and the build "hangs"). The Internal configuration defines OMNIS_INTERNAL and force-includes Core/Internal/InternalCompat.h into every file, which turns the external's process-handle calls (OpenProcess, ReadProcessMemory, VirtualQueryEx) into in-process ones.
  • OMNIS_INJECT_STAGE at the top of dllmain.cpp widens the startup for bisecting a crash: 1 = beep only, 2 = + backend/config, 3 = + entity threads, 4 = everything (normal).
  • Inject at the main menu only. R6 must run borderless or windowed (§7).
  • Logs (both in build\, previous run kept as .prev.log):
    • omnis_internal.log — every printf. Written through a pipe tee, so it can be read while the game runs, but it loses its last lines if the game dies.
    • omnis_crash.log — raw WriteFile, survives a crash. The vectored exception handler logs every exception with module+offset and thread id, and the one that killed the process is marked *** UNHANDLED … THIS killed the process. The overlay's first-time steps (GameOverlay::Mark) go here too, with thread ids, so a crash names the step it died in.
  • Eject: END — the overlay closes its window and D3D11/ImGui (GameOverlay::Stop), then the DLL frees itself.
  • Settings (Core/State/Config/Config.h): <game exe folder>\configs\<name>.ini (on this PC C:\Users\kajus\AppData\Local\ubisoft\r6s\configs), last.txt there names the one to load at inject. Changes autosave into the loaded config at most every 5 s, only when a setting changed (FNV hash over the settings structs). At load, ForceInternalSafe switches off what the internal cannot do (Team Check, Operator Names, Strict Filter, Require Skeleton, bone editor) so a saved "on" cannot act with no menu switch; Radar is forced off.

2. Build identity, signatures, the dumper's cfg

Core/SDK/EntityList.h, Core/SDK/DumpCfg.h

  • ReadBuildId() reads the running module's TimeDateStamp + SizeOfImage. Hard-coded RVAs (the cfg, kHomeStamp/kHomeImage) are only used when the build matches (RvasTrusted()). On any other build it logs *** UNSUPPORTED BUILD *** rather than reading random memory.
  • Where each value comes from, in order: (1) the dumper's cfg for this exact build, (2) the signatures, (3) the values compiled into the source. Nothing was removed when the cfg arrived — a build with no dump still runs on the signatures and built-ins, and any single value the cfg lacks (or that fails its check where it is used) falls through. The log says which source won ([dumpcfg] … from dumper cfg).
  • The dumper cfg (DumpCfg.h): dumper_<stamp>.cfg, looked for in Custom Dumper\bin\results\ then try\build\, then dumper.cfg in both if its build_stamp matches. It must match both build_stamp and build_image. Written by the dumper (below).
  • Signatures find classes; addresses are never trusted blindly. Pattern grammar (ParsePattern): 8D exact, ?? any, 4?/?5 nibble, C0&F8 bit mask (register-tolerant). ResolveVt scans .text, resolves every hit to a vtable (vt = hit + add + int32(@hit + disp)), drops insane ones (VtableSane: ≥ 6 of the first 8 slots point into the module), merges duplicates, and refuses if hits disagree.
  • The three classes (this build: 1 hit each, all agree):
classpatternresolve

CHARACTER00 00 FF FF FF 7F ?? 8D 0D ?? ?? ?? ?? 4C 89 09 48 8D 0D ??hit+13+i32(@hit+9)

(each has a fallback pattern in kEntSig/kCharSig/kDmgSig). On the second account's build (0xCFA6FE97) all of these missed — that is what the dumper is for.

The dumper — Custom Dumper ("KAYAZ DUMPER")

A separate exe, run in the shooting range. It only reads the game. Each step tells you what to do in-game, you press HOME in-game (DELETE skips), and it finds the value by behaviour — what moves when you walk, turn, run, shoot — never from a remembered address:

3. Camera

Core/State/ViewScan.h

  • The game's own render camera lives in a heap "view block". It is found by a 40-byte plaintext float constant tail (-0.99, 0, 0, 5, -5, 0, 0, 0.8, 0.5, 0.25), and view_block = hit - 0x2A4.
    • view_block + 0x190 = camera position (Vector3)
    • view_block + 0x250 = world→clip matrix, row-vector (clip = [x y z 1]·M), translation baked in — feed world coordinates directly.
  • This data anchor survived a recompile that moved 9.5 MB of code, when the code signature for the camera died. Prefer data anchors on this game.
  • The dumper checks this anchor every run. When it has died, the dumper's cfg carries a new anchor with its distances to the matrix and the eye, and the internal switches to it (ViewScan::ApplyDumpCfg); the old one is used while the cfg says it is still valid.
  • The last hit address is remembered; if the block goes stale it checks that address first (≈1 ms) before a full heap scan (1–5 s).
  • Per frame, Players::PlayersRender reads the matrix and eye itself (ViewScan::read_camera_batched) rather than trusting a copy another thread wrote: a 64-byte matrix copied without a lock can be read half-written, which showed as boxes jerking on mouse turns.
  • Proving a matrix is the camera, with no screen: the camera's own position maps to w = 0, and w == dot(pos − eye, forward) for every character. Trap: an all-zero float window also gives w = 0 exactly — storing every such hit once ran the machine out of memory and crashed the game. Always require a second, non-degenerate point in the same pass.
  • The matrix's depth row (this build): standard-Z, near 1 cm, far 1498 m (dumper step 6). Only the archived vis check used it.

4. Entity list — "character mode"

Core/SDK/EntityList.h

The object graph (this build)

ENTITY  (vtable from the ENTITY signature / dumper cfg)
  +0x20   facing quaternion (x, y, z, w), pure yaw, updated every frame
  +0xE0   pointer to component array
  +0xE8   component count  (& 0x3FFFFFFF)
     └─ components are identified by VTABLE, never by the u16 at ptr-8
        (that is a dlmalloc chunk header, it fooled us twice)
        CHARACTER component
          +0x1E0  feet position, updated EVERY FRAME          ← the box stands here
          (+0xA70 is a replicated copy at ~3 Hz — don't use)
        DAMAGE component
          +0x350  pointer to hit records   +0x358  record count
          record stride 0x78:  +0x68 damage dealt   +0x70 health before the hit
        SKELETON component (vtable 0x13F4E7D0)
          +0x2B8 → child +0xB0 → REST-pose palette  (its allocator header gives
          the bone count; the matrices themselves are identities)

The offsets are runtime variables (kCharPos, kCompArr, kCompCnt, kEntQuat, kDmgRecs, kDmgCnt, kRec*): built-in for this build, replaced by the dumper cfg when it has them (ApplyDumpCfg).

Sweep (every 3 s, own thread) — SweepCharacters

One pass over the heap collects every ENTITY (with its component array), every CHARACTER and every DAMAGE component by vtable. Each ENTITY's array is then tested by set membership (one read per entity). Output: character component addresses, character → damage, character → entity. The same pass also collects the skeleton's body-point classes (g_extra_vt, see §6.5).

In-process heap walks all go through EntityV2::ForEachHeapRegion (regions ≤ 128 MB, chunked guarded reads, a per-thread buffer). A private walker with 512 MB regions once killed the game silently.

Reader (every ~2 ms)

Per character:

  1. Read CHARACTER+0x1E0 (feet). Reject phantoms (all zero, non-finite, |v| > 10000).
  2. History advances only when the value changes (the old code stamped every poll and destroyed the interval). A jump > 8 m in one poll = respawn (range bots) → restart history and reset the health baseline.
  3. Health from the last hit record: hp = before − dealt (0 if negative), max = "before" of the first hit since the baseline. -1 = no hits = full, -2 = unknown. The baseline is the record count at the last respawn/revive. Heals only show at the next hit (its "before" includes the heal) — no current-health field is known yet.
  4. Facing: ENTITY+0x20, accepted if unit length.
  5. Dead check (menu "Dead Check"): see §5.

The ESP reads the list through EntityList::Get, which skips dead characters.

Why per-frame matters

Remote positions at the old offset (+0x160 on the list class) change only ~3.3 times a second — no read rate beats that. CHARACTER+0x1E0 changes every frame, so boxes need no prediction (per_frame = true bypasses the lerp).

5. Dead or alive (Dead Check)

EntityList.h reader + BotSkeleton.h pose report

  • The damage-component vtable flipping = certain death (dropped immediately).
  • Otherwise, with Dead Check on:
    • dead = (health 0 and the body is not standing) or (facing and position perfectly still for 4 s and the body is lying). Living players' facing changes 20–120 times a second; corpses 0.1.
    • It stays dead until a revive: the body stands again 2.5 s after health hit 0 (range dummies "never die"; revives), or it moves 0.5 m. A revive with health 0 resets the health baseline so the bar reads full.
    • "Lying / standing" comes from the skeleton worker (EntityList::g_pose: rig top < 0.7 m / > 1.2 m). Skeletons off → health 0 alone decides.
  • Dead characters stay on the list, flagged. The ESP skips them, and the skeleton worker keeps their rig bound to their own corpse — which is what stops a dead player's skeleton being handed to someone alive.
  • Health "before − dealt" is not capped at 300 damage (headshots/explosions exceed it; capping turned kills into "unknown").

6. Skeletons

Core/SDK/BotSkeleton.h (worker thread) → Core/Game/Players/Players.h (drawing)

6.1 What the bone data is

  • Every character's collision rig: a run of 30–40 4×4 float matrices, stride 0x40. Rows at +0/+0x10/+0x20 unit length, +0x3C == 1, bone position at +0x30. Model space: origin at the feet, +x = body's right, +y = forward, +z = up. Row 2 is the bone's axis and points at its child.
  • It has no names, no owner pointer, and a new address every tick (never cache one). Old copies stay in memory until reused.
  • Rigs differ per operator: one match had 31, 32 (three builds), 33, 34 bones; a 10-character session saw 31–38. Range bots: 32. You: 33 (34 at times).
  • The rest-pose palette reachable from each character (§4) gives that character's bone count only — its matrices are identities (the dumper measures their spread as 0.00), so it cannot tell two same-count operators apart.
  • Named render skeletons exist in CPU memory only for the local player (value finder, 2026-09-23). Bone name hashes are crc32(name) and never change, but they don't apply to this rig.

6.2 Finding palettes (every 4 ms)

  • Arenas: private RW regions of exactly 0x200000 bytes that contained a palette. Relearned every 5 s (palettes rotate between arenas) and unioned with the previous set.
  • Windowed reads: each arena remembers the span where palettes landed in the last second; most passes read that span ±128 KB, every 8th pass reads the whole arena.
  • ScanArena: every 16-byte phase, runs of valid matrices; a palette is 30–40 elements shaped like a body in ANY pose (longest extent 0.9–2.6 m, height > 0.15 m — a "taller than 0.9 m" test threw away every prone body).
  • Birth time: when a palette address first showed its current contents (kept 2 s). Used so the newest copy always wins.

6.3 Templates — recognising the same body every tick

  • A body's slot order is fixed for its life and differs between bodies, so a template = one body. It holds the rigid links (bone → child along its axis), their lengths, the latest pose and the clean skeleton map.
  • Derive (Derive): child(i) = nearest bone within 0.02–0.90 m that bone i's axis points at (cos ≥ 0.95), plus spine reconnects. No extra filters (rejecting mutual pairs once made every palette fail).
  • New template when a palette matches no template and either its link lengths match a known rig list (32-bone bots: kRef32), or — for a rig never seen — the frame maps cleanly onto the skeleton (§6.4). One clean frame is enough; waiting for three identical standing frames made round starts take ages. A new rig's length list is then known for everyone who uses it.
  • Matching a palette to a template: count rigid links whose length holds within 2.5 cm (1 cm froze running bodies). Needs ≥ 60% of the links still in use (min 8) and ≥ 3× the best non-duplicate template. A link is retired as a sliding helper only if it misses in > 30% of 20+ matches.
  • Duplicates: a derivation sharing ≥ 50% of links with an existing template IS that template (different bodies share 0–3 of 26). Without this, copies of one template multiplied to 469.
  • Newest palette wins: matches are collected, then each template takes the newest matched palette, and never one older than what's already shown.

6.4 The clean skeleton (the lines you see)

Raw axis links look wrong on this rig (spine bones are sideways capsules → no spine, chest diagonals, flat pelvis), so they are never drawn.

  • Exact maps for known rigs, labelled by hand from renders:
    • 32-bone (range bots): head 0, neck 4, pelvis 11; R arm 16-1-22-17; L arm 21-5-30-19 (19 = left hand on the foregrip); L leg 28-9-3-8-10-2; R leg 24-6-26-15-14-27.
    • 33-bone (your rig): head 30, neck 11, pelvis 13; R 11-9-1-31; L 11-28-22-15; L leg 13-5-8-2-0-32-25; R leg 13-12-19-4-26-6-18.
    • Mapped per template by Hungarian assignment on positions, accepted if ≥ 20/26 rigid lengths hold (12% tolerance) and mean position error ≤ 10 cm.
  • Generic 17-joint map for every other rig: canonical joints (head, neck, pelvis, shoulders, elbows, hands, hips, knees, ankles, toes) → nearest b
