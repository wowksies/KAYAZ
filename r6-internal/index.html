Omnis R6 Internal

An internal for Siege that runs inside the game process. It's still in development, but it already runs on all QB's with full player ESP, and chams are on the way.

what it is

Omnis R6 Internal is the internal version of Omnis for Rainbow Six Siege. The R6 External reads everything from outside the game, but this one runs inside it, so it has direct access to the game's data.

It works with BattlEye running and on all QB's. Right now the focus is visuals: health, box and skeleton ESP on every player, and chams are being worked on next.

How the internal works — camera to skeleton

deep dive: how the internal actually works — the writeup that lives with the code

Written 2026-09-24, when the internal was working end to end: camera, boxes that move every frame, health bars, dead check, and skeletons on every operator in a real match. Last updated 2026-09-27: own overlay window instead of the DX12 hook (§7), the binding fix for crowded scenes (§6.5), aimbot and menu written up (§8, §9).

Addresses, offsets and anchors change per build and per account. This writeup sticks to how the pieces fit together and what each stage is responsible for — the actual bytes, offsets and finder anchors are not published.

0. The pipeline at a glance

inject at main menu
   │
   ├─ STARTUP THREAD (dllmain.cpp)       console + log, attach, config, then everything below
   │
   ├─ OVERLAY THREAD (overlay_window.cpp) own D3D11 window over R6, no hooks
   │     every refresh: menu + ESP + skeleton drawing + aimbot  (OnFrame → Players.h)
   │
   ├─ CAMERA  (ViewScan.h)               view block → cam pos + world→clip matrix
   │
   ├─ ENTITY LIST (EntityList.h)
   │     class discovery → ENTITY / CHARACTER / DAMAGE
   │     periodic heap sweep → which ENTITYs own a CHARACTER (+ DAMAGE)
   │     fast reader → feet position, facing, health, dead/alive
   │
   ├─ ESP (EntityCache.h → Players.h)    boxes, head circle, health bar, distance
   │
   └─ SKELETONS (BotSkeleton.h, own worker thread)
         arenas → bone palettes (model space, no names, no owner)
         templates = one per body (recognised by rigid bone lengths)
         clean skeleton = hand-labelled or generic 17-joint map per template
         binding = which template belongs to which character (fit + camera + ownership)
         placement = feet + rotate(facing, bone)  → drawn by Players.h

Startup order matters: the overlay starts first and its first drawn frame is the signal that R6 is past startup; only then do the scans begin (scanning while R6 is still paging in / compiling shaders hit uncommitted pages and crashed uncatchably). The legacy GetGameState thread (EntityCache's old round-state system) is off — every early crash died in its discovery pass and the ESP needs nothing from it.

1. Build, inject, logs, eject

  • Build only Dominate.vcxproj /p:Configuration=Internal /p:Platform=x64 (PowerShell MSBuild). Release|x64 is the external — never build it. Output: build\Omnis_R6.dll. Pipe MSBuild to a file, never to Select-Object -First (that orphans cl.exe and the build "hangs"). The Internal configuration defines OMNIS_INTERNAL and force-includes an internal-compat header into every file, which turns the external's process-handle calls (OpenProcess, ReadProcessMemory, VirtualQueryEx) into in-process ones.
  • OMNIS_INJECT_STAGE at the top of dllmain.cpp widens the startup for bisecting a crash: 1 = beep only, 2 = + backend/config, 3 = + entity threads, 4 = everything (normal).
  • Inject at the main menu only. R6 must run borderless or windowed (§7).
  • Logs (both in build\, previous run kept as .prev.log):
    • omnis_internal.log — every printf. Written through a pipe tee, so it can be read while the game runs, but it loses its last lines if the game dies.
    • omnis_crash.log — raw WriteFile, survives a crash. The vectored exception handler logs every exception with module+offset and thread id, and the one that killed the process is marked *** UNHANDLED … THIS killed the process. The overlay's first-time steps (GameOverlay::Mark) go here too, with thread ids, so a crash names the step it died in.
  • Eject: END — the overlay closes its window and D3D11/ImGui (GameOverlay::Stop), then the DLL frees itself.
  • Settings: <game exe folder>\configs\<name>.ini, last.txt there names the one to load at inject. Changes autosave into the loaded config at most every 5 s, only when a setting changed (FNV hash over the settings structs). At load, ForceInternalSafe switches off what the internal cannot do (Team Check, Operator Names, Strict Filter, Require Skeleton, bone editor) so a saved "on" cannot act with no menu switch; Radar is forced off.

2. Build identity, discovery, the dumper's cfg

  • ReadBuildId() reads the running module's TimeDateStamp + SizeOfImage. Hard-coded RVAs are only used when the build matches (RvasTrusted()). On any other build it logs *** UNSUPPORTED BUILD *** rather than reading random memory.
  • Where each value comes from, in order: (1) the dumper's cfg for this exact build, (2) the built-in discovery pass, (3) the values compiled into the source. Nothing was removed when the cfg arrived — a build with no dump still runs on discovery and built-ins, and any single value the cfg lacks (or that fails its check where it is used) falls through. The log says which source won ([dumpcfg] … from dumper cfg).
  • The dumper cfg: dumper_<stamp>.cfg, looked for in Custom Dumper\bin\results\ then try\build\, then dumper.cfg in both if its build_stamp matches. It must match both build_stamp and build_image. Written by the dumper (below).
  • Discovery finds classes; addresses are never trusted blindly. The finder scans .text, resolves every candidate to a vtable, drops insane ones (a sanity check on the first vtable slots, requiring most of them to point into the module), merges duplicates, and refuses if candidates disagree.

The dumper — "KAYAZ DUMPER"

A separate exe, run in the shooting range. It only reads the game. Each step tells you what to do in-game, you press HOME in-game (DELETE skips), and it finds the value by behaviour — what moves when you walk, turn, run, shoot — never from a remembered address:

stepyou doit finds
1 camerastand, walk 3 m, turn 90°, look up 45°the camera and view matrix, plus a fresh anchor for them; checks the internal's old anchor
2 playersbots running, then you runthe CHARACTER class + position field (what moves with bots and you every frame), and the ENTITY that owns them
3 facingturn 90° in placethe facing quaternion (entity or character)
4 healthshoot one bot twicethe DAMAGE component + hit record layout (a list that grows by one record per hit)
5 skeleton chainbots runningcomponent → child → rest palette (bone count per character); whether a live link exists

Output: results\dump_<stamp>_<time>.txt (for you), results\dumper.cfg and results\dumper_<stamp>.cfg (for the internal). Two accounts run two builds; the per-stamp file keeps both.

3. Camera

  • The game's own render camera lives in a heap "view block". Once found, it gives the camera position and the world→clip matrix (row-vector, translation baked in — feed world coordinates directly).
  • Data anchors survive recompiles that move a lot of code, when a code-based finder for the same value dies. Prefer data anchors on this game.
  • The dumper re-checks the anchor every run. When it has died, the dumper's cfg carries a new anchor and the internal switches to it (ViewScan::ApplyDumpCfg); the old one is used while the cfg says it is still valid.
  • The last hit address is remembered; if the block goes stale it checks that address first (≈1 ms) before a full heap scan (1–5 s).
  • Per frame, Players::PlayersRender reads the matrix and eye itself (ViewScan::read_camera_batched) rather than trusting a copy another thread wrote: a 64-byte matrix copied without a lock can be read half-written, which showed as boxes jerking on mouse turns.
  • Proving a matrix is the camera, with no screen: the camera's own position maps to w = 0, and w == dot(pos − eye, forward) for every character. Trap: an all-zero float window also gives w = 0 exactly — storing every such hit once ran the machine out of memory and crashed the game. Always require a second, non-degenerate point in the same pass.

4. Entity list — "character mode"

The object graph

An ENTITY carries a facing quaternion (pure yaw, updated every frame) and owns a component array. Components are identified by vtable, never by the allocator's chunk header (that fooled us twice). The three that matter:

  • CHARACTER — carries the feet position, updated every frame. That's where the box stands. There is also a replicated copy that ticks a few times a second; don't use it.
  • DAMAGE — carries a growing list of hit records (damage dealt and health before the hit, per record).
  • SKELETON — reaches a rest-pose palette whose allocator header gives the character's bone count. The matrices themselves are identities, so the palette can't tell same-count operators apart.

Every layout value is a runtime variable, built in for the current build and replaced by the dumper cfg when it has them (ApplyDumpCfg).

Sweep (periodic, own thread) — SweepCharacters

One pass over the heap collects every ENTITY (with its component array), every CHARACTER and every DAMAGE component by vtable. Each ENTITY's array is then tested by set membership (one read per entity). Output: character component addresses, character → damage, character → entity. The same pass also collects the skeleton's body-point classes (g_extra_vt, see §6.5).

In-process heap walks all go through EntityV2::ForEachHeapRegion (bounded regions, chunked guarded reads, a per-thread buffer). A private walker with much larger regions once killed the game silently.

Reader (fast tick)

Per character:

  1. Read the CHARACTER's feet field. Reject phantoms (all zero, non-finite, absurdly far).
  2. History advances only when the value changes (the old code stamped every poll and destroyed the interval). A jump greater than 8 m in one poll = respawn (range bots) → restart history and reset the health baseline.
  3. Health from the last hit record: hp = before − dealt (0 if negative), max = "before" of the first hit since the baseline. -1 = no hits = full, -2 = unknown. The baseline is the record count at the last respawn/revive. Heals only show at the next hit (its "before" includes the heal) — no current-health field is known yet.
  4. Facing: read from the ENTITY, accepted if unit length.
  5. Dead check (menu "Dead Check"): see §5.

The ESP reads the list through EntityList::Get, which skips dead characters.

Why per-frame matters

Some replicated fields the old code chased change only ~3.3 times a second — no read rate beats that. The CHARACTER's own feet field changes every frame, so boxes need no prediction (per_frame = true bypasses the lerp).

5. Dead or alive (Dead Check)

  • The damage-component vtable flipping = certain death (dropped immediately).
  • Otherwise, with Dead Check on:
    • dead = (health 0 and the body is not standing) or (facing and position perfectly still for 4 s and the body is lying). Living players' facing changes 20–120 times a second; corpses 0.1.
    • It stays dead until a revive: the body stands again 2.5 s after health hit 0 (range dummies "never die"; revives), or it moves 0.5 m. A revive with health 0 resets the health baseline so the bar reads full.
    • "Lying / standing" comes from the skeleton worker (EntityList::g_pose: rig top under ~0.7 m / over ~1.2 m). Skeletons off → health 0 alone decides.
  • Dead characters stay on the list, flagged. The ESP skips them, and the skeleton worker keeps their rig bound to their own corpse — which is what stops a dead player's skeleton being handed to someone alive.
  • Health "before − dealt" is not capped at 300 damage (headshots/explosions exceed it; capping turned kills into "unknown").

6. Skeletons

6.1 What the bone data is

  • Every character's collision rig is a run of 4×4 float matrices, one per bone. Model space: origin at the feet, +x = body's right, +y = forward, +z = up. Each row is a bone axis; the axis of interest points at the child.
  • It has no names, no owner pointer, and a new address every tick (never cache one). Old copies stay in memory until reused.
  • Rigs differ per operator: a 10-character session saw counts spread across a range. Range bots and your own rig sit inside that range too.
  • The rest-pose palette reachable from each character (§4) gives that character's bone count only — its matrices are identities, so it cannot tell two same-count operators apart.
  • Named render skeletons exist in CPU memory only for the local player (value finder, 2026-09-23). Bone name hashes are crc32(name) and never change, but they don't apply to this rig.

6.2 Finding palettes (every 4 ms)

  • Arenas: private RW regions of a fixed size that once contained a palette. Relearned every 5 s (palettes rotate between arenas) and unioned with the previous set.
  • Windowed reads: each arena remembers the span where palettes landed in the last second; most passes read that span with a small margin, every 8th pass reads the whole arena.
  • ScanArena: on a fixed byte cadence, runs of valid matrices; a palette is shaped like a body in ANY pose (longest extent in a plausible human range, minimum vertical extent). A "taller than 0.9 m" test threw away every prone body — the test now allows lying poses.
  • Birth time: when a palette address first showed its current contents (kept 2 s). Used so the newest copy always wins.

6.3 Templates — recognising the same body every tick

  • A body's slot order is fixed for its life and differs between bodies, so a template = one body. It holds the rigid links (bone → child along its axis), their lengths, the latest pose and the clean skeleton map.
  • Derive (Derive): child(i) = nearest bone within a plausible bone-length range that bone i's axis points at, plus spine reconnects. No extra filters (rejecting mutual pairs once made every palette fail).
  • New template when a palette matches no template and either its link lengths match a known rig list, or — for a rig never seen — the frame maps cleanly onto the skeleton (§6.4). One clean frame is enough; waiting for three identical standing frames made round starts take ages. A new rig's length list is then known for everyone who uses it.
  • Matching a palette to a template: count rigid links whose length holds within a small tolerance (a tighter tolerance froze running bodies). Needs a majority of the links still in use and several times the score of the best non-duplicate template. A link is retired as a sliding helper only if it misses in too many consecutive matches.
  • Duplicates: a derivation sharing enough links with an existing template IS that template (different bodies overlap barely at all on this rig). Without this, copies of one template multiplied to 469.
  • Newest palette wins: matches are collected, then each template takes the newest matched palette, and never one older than what's already shown.

6.4 The clean skeleton (the lines you see)

Raw axis links look wrong on this rig (spine bones are sideways capsules → no spine, chest diagonals, flat pelvis), so they are never drawn.

  • Exact maps for known rigs, labelled by hand from renders. Each map is a named per-joint list (head, neck, pelvis, arms, legs) for one specific bone count. New rigs get a new map as they show up.
  • Maps are attached to a template by Hungarian assignment on positions, accepted when enough rigid lengths hold within tolerance and the mean position error is small.
  • Generic 17-joint map for every other rig: canonical joints (head, neck, pelvis, shoulders, elbows, hands, hips, knees, ankles, toes) → nearest b
