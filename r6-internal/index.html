what it is

Kayaz R6 Internal is my internal for Rainbow Six Siege. The R6 External reads everything from outside the game, but this one runs inside it, so it has direct access to the game's data.

It works with BattlEye running and on all QB's. Right now the focus is visuals: health, box and skeleton ESP on every player, and chams are being worked on next.

How the internal works, camera to skeleton

Written 2026-09-24, when the internal was working end to end: camera, boxes that move every frame, health bars, dead check, and skeletons on every operator in a real match. Last updated 2026-09-27: own overlay window instead of the DX12 hook (§7), the binding fix for crowded scenes (§6.5), aimbot and menu written up (§8, §9).

Addresses, offsets and anchors move around per build and per account, so this writeup only talks about the shape of the thing. No bytes, no offsets, no anchors.

0. The pipeline at a glance

inject at main menu
   │
   ├─ STARTUP THREAD (dllmain.cpp)       console + log, attach, config, then everything below
   │
   ├─ OVERLAY THREAD (overlay_window.cpp) own D3D11 window over R6, no hooks
   │     every refresh: menu + ESP + skeleton drawing + aimbot  (OnFrame → Players.h)
   │
   ├─ CAMERA  (ViewScan.h)               view block → cam pos + world→clip matrix
   │
   ├─ ENTITY LIST (EntityList.h)
   │     class discovery → ENTITY / CHARACTER / DAMAGE
   │     periodic heap sweep → which ENTITYs own a CHARACTER (+ DAMAGE)
   │     fast reader → feet position, facing, health, dead/alive
   │
   ├─ ESP (EntityCache.h → Players.h)    boxes, head circle, health bar, distance
   │
   └─ SKELETONS (BotSkeleton.h, own worker thread)
         arenas → bone palettes (model space, no names, no owner)
         templates = one per body (recognised by rigid bone lengths)
         clean skeleton = hand-labelled or generic 17-joint map per template
         binding = which template belongs to which character (fit + camera + ownership)
         placement = feet + rotate(facing, bone)  → drawn by Players.h

Threads

Startup order matters. The overlay starts first, and its first drawn frame tells everyone else R6 is past startup. Only then do the scans begin. Scanning while R6 is still paging in and compiling shaders hit uncommitted pages and crashed uncatchably. The legacy GetGameState thread (EntityCache's old round-state system) is off. Every early crash died in its discovery pass, and the ESP needs nothing from it.

1. Build, inject, eject

  • Build only Dominate.vcxproj /p:Configuration=Internal /p:Platform=x64 (PowerShell MSBuild). Release|x64 is the external. Never build it. Output: build\Omnis_R6.dll. Pipe MSBuild to a file, never to Select-Object -First (that orphans cl.exe and the build "hangs"). The Internal configuration defines OMNIS_INTERNAL and force-includes an internal-compat header into every file, which turns the external's process-handle calls (OpenProcess, ReadProcessMemory, VirtualQueryEx) into in-process ones.
  • OMNIS_INJECT_STAGE at the top of dllmain.cpp widens the startup for bisecting a crash: 1 = beep only, 2 = + backend/config, 3 = + entity threads, 4 = everything (normal).
  • Inject at the main menu only. R6 must run borderless or windowed (§7).
  • Eject: END. The overlay closes its window and D3D11/ImGui (GameOverlay::Stop), then the DLL frees itself.
  • Settings: <game exe folder>\configs\<name>.ini. last.txt there names the one to load at inject. Changes autosave into the loaded config at most every 5 s, and only when something actually changed (FNV hash over the settings structs). At load, ForceInternalSafe switches off what the internal cannot do (Team Check, Operator Names, Strict Filter, Require Skeleton, bone editor) so a saved "on" cannot act with no menu switch. Radar is forced off.

2. Build identity, discovery, the dumper

  • ReadBuildId() reads the running module's TimeDateStamp and SizeOfImage. Hard-coded RVAs only get used when the build matches (RvasTrusted()). On any other build it logs *** UNSUPPORTED BUILD *** instead of reading random memory.
  • Values come from three places in this order: the dumper's cfg for this exact build, the built-in discovery pass, and last the values compiled into the source. Nothing was removed when the cfg arrived. A build with no dump still runs on discovery and built-ins, and any single value the cfg lacks (or that fails its check where it is used) falls through.
  • Discovery finds classes, not addresses. Addresses are never trusted blindly. Every candidate is resolved to a vtable, run through a sanity check on the first slots, deduplicated, and rejected outright if candidates disagree.

Why there is a dumper

The internal has to run on more than one build. Two accounts already run two different builds, and every game update creates another one. Any offset or signature compiled into the source can stop matching between one launch and the next. Rewriting the source and shipping a new DLL each time is not a workflow.

The dumper is a tiny separate exe that runs in the shooting range. It reads the game only. What it produces is a per-build config file the internal loads at inject. When the game updates and something the internal relies on has moved, you run the dumper once in the range, and the internal picks up the new values on next inject. The source stays the same.

Two accounts means two builds, so the dumper writes both a generic dumper.cfg and a per-stamp dumper_<stamp>.cfg. The internal only accepts a cfg whose build_stamp and build_image match the running module.

3. Camera

  • The game's own render camera lives in a heap "view block". Once found, it gives the camera position and the world→clip matrix (row-vector, translation baked in, so world coordinates go straight in).
  • Data anchors outlive recompiles that shift a lot of code around, when a code-based finder for the same value dies. Prefer data anchors on this game.
  • The dumper re-checks the anchor every run. If it has died, the dumper's cfg carries a new one and the internal switches to it (ViewScan::ApplyDumpCfg). The old one is used while the cfg says it is still valid.
  • The last hit address is remembered. If the block goes stale it checks that address first (about 1 ms) before a full heap scan (1 to 5 s).
  • Per frame, Players::PlayersRender reads the matrix and eye itself (ViewScan::read_camera_batched) rather than trusting a copy another thread wrote. A 64-byte matrix copied without a lock can be read half-written, which showed as boxes jerking on mouse turns.
  • Proving a matrix is the camera, with no screen: the camera's own position maps to w = 0, and w == dot(pos − eye, forward) for every character. Trap: an all-zero float window also gives w = 0 exactly. Storing every such hit once ran the machine out of memory and crashed the game. Always require a second, non-degenerate point in the same pass.

4. Entity list, "character mode"

The object graph

An ENTITY carries a facing quaternion (pure yaw, updated every frame) and owns a component array. Components are identified by vtable, never by the allocator's chunk header. That fooled us twice. The three components that matter:

  • CHARACTER, carries the feet position, updated every frame. That is where the box stands. There is also a replicated copy that ticks a few times a second. Don't use it.
  • DAMAGE, carries a growing list of hit records (damage dealt and health before the hit, per record).
  • SKELETON, reaches a rest-pose palette whose allocator header gives the character's bone count. The matrices themselves are identities, so the palette can't tell same-count operators apart.

Every layout value is a runtime variable, built in for the current build and replaced by the dumper cfg when it has them (ApplyDumpCfg).

Sweep (periodic, own thread), SweepCharacters

One pass over the heap collects every ENTITY (with its component array), every CHARACTER and every DAMAGE component by vtable. Each ENTITY's array is then tested by set membership, one read per entity. Output: character component addresses, character → damage, character → entity. The same pass also collects the skeleton's body-point classes (g_extra_vt, see §6.5).

In-process heap walks all go through EntityV2::ForEachHeapRegion (bounded regions, chunked guarded reads, a per-thread buffer). A private walker with much larger regions once killed the game silently.

Reader (fast tick)

Per character:

  1. Read the CHARACTER's feet field. Reject phantoms (all zero, non-finite, absurdly far).
  2. History advances only when the value changes. The old code stamped every poll and destroyed the interval. A jump greater than 8 m in one poll means respawn (range bots), so restart history and reset the health baseline.
  3. Health from the last hit record: hp = before − dealt (0 if negative), max is the "before" of the first hit since the baseline. -1 means no hits so full, -2 means unknown. The baseline is the record count at the last respawn or revive. Heals only show at the next hit (its "before" includes the heal). No current-health field is known yet.
  4. Facing: read from the ENTITY, accepted if unit length.
  5. Dead check (menu "Dead Check"), see §5.

The ESP reads the list through EntityList::Get, which skips dead characters.

Why per-frame matters

Some replicated fields the old code chased change only about 3.3 times a second. No read rate beats that. The CHARACTER's own feet field changes every frame, so boxes need no prediction (per_frame = true bypasses the lerp).

5. Dead or alive (Dead Check)

  • The damage-component vtable flipping is certain death. Dropped immediately.
  • Otherwise, with Dead Check on:
    • Dead when health is 0 and the body is not standing, or when facing and position are perfectly still for 4 s and the body is lying. Living players' facing changes 20 to 120 times a second. Corpses do 0.1.
    • It stays dead until a revive. The body stands again 2.5 s after health hit 0 (range dummies "never die", revives), or it moves 0.5 m. A revive with health 0 resets the health baseline so the bar reads full.
    • "Lying" and "standing" come from the skeleton worker (EntityList::g_pose, rig top under about 0.7 m and over about 1.2 m). Skeletons off, health 0 alone decides.
  • Dead characters stay on the list, flagged. The ESP skips them, and the skeleton worker keeps their rig bound to their own corpse. That is what stops a dead player's skeleton being handed to someone alive.
  • Health "before − dealt" is not capped at 300 damage (headshots and explosions exceed it). Capping turned kills into "unknown".

6. Skeletons

6.1 What the bone data is

  • Every character's collision rig is a run of 4×4 float matrices, one per bone. Model space: origin at the feet, +x is the body's right, +y is forward, +z is up. Each row is a bone axis. The axis of interest points at the child.
  • No names, no owner pointer, and a new address every tick. Never cache one. Old copies stay in memory until reused.
  • Rigs differ per operator. A 10-character session saw counts spread across a range. Range bots and your own rig sit inside that range too.
  • The rest-pose palette reachable from each character (§4) gives that character's bone count only. Its matrices are identities, so it can't tell two same-count operators apart.
  • Named render skeletons exist in CPU memory only for the local player (value finder, 2026-09-23). Bone name hashes are crc32(name) and never change, but they don't apply to this rig.

6.2 Finding palettes (every 4 ms)

  • Arenas: private RW regions of a fixed size that once contained a palette. Relearned every 5 s (palettes rotate between arenas) and unioned with the previous set.
  • Windowed reads: each arena remembers the span where palettes landed in the last second. Most passes read that span with a small margin. Every 8th pass reads the whole arena.
  • ScanArena: on a fixed byte cadence, runs of valid matrices. A palette is shaped like a body in ANY pose (longest extent in a plausible human range, minimum vertical extent). A "taller than 0.9 m" test threw away every prone body. The test now allows lying poses.
  • Birth time: when a palette address first showed its current contents (kept 2 s). Used so the newest copy always wins.

6.3 Templates, recognising the same body every tick

  • A body's slot order is fixed for its life and differs between bodies, so a template = one body. It holds the rigid links (bone → child along its axis), their lengths, the latest pose and the clean skeleton map.
  • Derive (Derive): child(i) is the nearest bone within a plausible bone-length range that bone i's axis points at, plus spine reconnects. No extra filters. Rejecting mutual pairs once made every palette fail.
  • New template when a palette matches no template and either its link lengths match a known rig list, or, for a rig never seen, the frame maps cleanly onto the skeleton (§6.4). One clean frame is enough. Waiting for three identical standing frames made round starts take ages. A new rig's length list is then known for everyone who uses it.
  • Matching a palette to a template: count rigid links whose length holds within a small tolerance (a tighter tolerance froze running bodies). Needs a majority of the links still in use, and several times the score of the best non-duplicate template. A link is retired as a sliding helper only if it misses in too many consecutive matches.
  • Duplicates: a derivation sharing enough links with an existing template IS that template (different bodies overlap barely at all on this rig). Without this, copies of one template multiplied to 469.
  • Newest palette wins. Matches are collected, then each template takes the newest matched palette, and never one older than what's already shown.

6.4 The clean skeleton (the lines you see)

Raw axis links look wrong on this rig (spine bones are sideways capsules, so no spine, chest diagonals, flat pelvis). They are never drawn.

  • Exact maps for known rigs, labelled by hand from renders. Each map is a named per-joint list (head, neck, pelvis, arms, legs) for one specific bone count. New rigs get a new map as they show up.
  • Maps are attached to a template by Hungarian assignment on positions, accepted when enough rigid lengths hold within tolerance and the mean position error is small.
  • Generic 17-joint map for every other rig. Canonical joints (head, neck, pelvis, shoulders, elbows, hands, hips, knees, ankles, toes) get matched to the nearest bones. It's only accepted when the pose is close to standing, heights are in the right order, left is actually left of right, and limb lengths are sane. It retries every match until it gets a good frame.
  • Dots (2026-09-27): a body that has lines to draw gets no bone dots. Dots only show on a body whose skeleton hasn't been learned yet, so it doesn't vanish in the meantime. Solid mode never draws dots.
  • The head circle sits 30% of the way from the crown bone to the neck.

6.5 Binding, which template belongs to which character

  • Body points: world matrices that sit on characters. Their classes are worked out at runtime (DeriveBody) by looking for matrices that stay right next to the feet on most bots, and they get re-derived when they come up sparse. The entity sweep collects the instances, and every second the list is filtered down to the ones near a character. The entity class alone has around 27k instances, and cutting that list short once starved the fit.
  • Which character a point belongs to (NearFeet): the nearest character, horizontally, whose box holds it. A point sitting almost exactly between two characters gets dropped. Until 2026-09-27 it was the first character in the list whose box held it, so two players standing close meant one of them collected both bodies' points. More on that below.
  • Bone count rule: a template is never bound to a character whose rest palette has a different bone count. If no template with that count has shown up for 15 s, the rule is dropped for that character instead of leaving it bare.
  • Fit: every body point is taken into the character's model frame and measured against the nearest segment of the template's clean skeleton, averaged and smoothed over time. Lower is better. A right pairing usually reads around 10 to 18 cm.
  • You compete too, as a claimant scored by the camera (where the camera sits in your model frame vs the rig's head point). Whatever you win is never drawn, and once your rig is locked to you, you take nothing else.
  • Assignment: Hungarian over templates × (characters + you). The cost is the fit, with a small stickiness bonus for the current pairing.
  • Ownership: bound to the same body for 2 s, and fitting it clearly better than every other body for the last 1.5 s straight, means locked to that body. Owner gone for 1.5 s means retired. Retired but moving like a living body for 2.5 s means it was a wrong lock, so it gets revived. Owner fitting clearly worse than another body for 1.5 s means unlocked. A new round (at least half the characters are new) clears every template.
  • The 2026-09-27 fix for crowded scenes. A 10-character session had 60 locks, and 27 of them later unlocked because they fit another body better. That's 45% wrong, each one sitting on the wrong player for 3 s or more. Almost every lock came in right at the old 3 cm minimum margin, and with points shared between neighbours that margin was just noise. Three changes fixed it: nearest-character points (above), a 5 cm margin held for 1.5 s to lock (was 3 cm at one instant), and an 8 cm margin for 1.5 s to unlock (was 12 cm for 3 s). The shooting range never shows this because its bots stand apart, so Versus AI is where to test it.

6.6 Smooth motion

  • Pose changes land every 5 to 20 ms. A running foot swings from behind the body to in front and back in about 150 ms. Facing changes 60 to 120 times a second.
  • The drawn pose blends from what's on screen to the newest pose over ¾ of the gap since the previous change (60 ms max). Re-reads that didn't change don't count as new samples.
  • Placement (BotSkeleton::Place): world = feet + rotate(q, bone), where rotate(q, v) = v + 2u×(u×v + w v) and q is the entity's facing quaternion, applied directly (the model faces +y and q already includes that). Feet is the box's own base position, so the rig can't drift off the box.
  • Place() fills the old skeleton struct, so the existing drawing code (lines, solid mode, head circle, the aimbot's head point) just uses it.

6.7 Vis check, archived

It worked, reading the depth buffer, but it needs R6's GPU queue, and the internal doesn't hook anything anymore (§7). So it's archived.

7. Rendering, our own overlay window

Since 2026-09-27 nothing of R6's is hooked. No Present hook, no queue hooks, no WndProc subclass. The DLL imports d3d11.dll and dwmapi.dll, and no d3d12.dll, MinHook or kiero.

Window

  • The overlay thread makes itself per-monitor DPI aware first. Without that, the window came out 1920x1080 "logical" on a scaled 2560x1440 screen and Windows stretched it.
  • It waits for R6's main window: this process, visible, unowned, not the console, biggest client area.
  • It creates a borderless topmost popup exactly over R6's client area. WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW makes it click-through with no taskbar button, and DwmExtendFrameIntoClientArea(-1) plus clearing to alpha 0 makes it see-through. ImGui's blending writes premultiplied colour and alpha, which is what DWM composites. Alt+F4 and Alt do nothing on it.

Device and frame

  • Own D3D11 device and a DISCARD swap chain (B8G8R8A8), Present(1) for one frame per refresh, max frame latency 1, Alt+Enter disabled. Own ImGui context.
  • Fonts are built before the first frame. Built mid-frame, DX11 frees the old font texture while that frame's draw lists still point at it.
  • No icon textures in the DLL. Loading them goes through COM (WIC), and the shim engine then crashed R6 (see §11). The menu draws its tab icons as vectors instead.
  • Each frame: follow R6's client rect (move, resize, update the resolution for world-to-screen), hide while neither R6 nor our window is in front (alt-tab, minimised), re-assert topmost once a second, then NewFrame → OnFrame → Present. OnFrame does the menu, config autosave, watermark, Players::PlayersRender (ESP, skeletons, aimbot) and the "loaded" pill.

Input

  • INSERT toggles the menu. It watches the key's high bit, because the low "pressed since" bit gets eaten by other readers. Open means the window stops being click-through, so clicks reach ImGui. It doesn't grab focus by itself, but clicking it does, which you need to type a config name. Closed means click-through again, with focus handed back to R6 if we had it. If focus leaves the open menu (alt-tab), the menu closes, so the window can't sit there eating R6's clicks.
  • The menu starts closed. A "kayaz.xyz loaded, INSERT opens the menu" pill shows at the top for 8 s.

The cost of doing it this way

Windows composites the window over the game, so it shows about a frame after the game's own image, and the ESP can trail a fast turn. ESP Lead makes up for that. Over true exclusive fullscreen nothing shows at all.

9. Aimbot

  • Target: every live character within Max Distance. Its aim point is the head circle's centre, found the same way the circle finds it: the bound skeleton's head point, or if there's no skeleton, a fixed-height guess (box top plus one head radius). Whichever is nearest the screen centre within FOV pixels wins.
  • Only fires while right and left mouse are both held, so aiming down sights and shooting. Aimbot.AimKey is saved in the config but this check doesn't use it.
  • Movement: relative mouse moves with SendInput, with frame-rate independent exponential smoothing. The time constant is Smoothness × 13 ms (1 is about instant, 100 is about 1.3 s), plus a small dead zone once it's on the head so it doesn't buzz.
  • Unlock Y-Axis: despite the name, on means no vertical movement. The code zeroes the vertical step when it's set, so it's horizontal-only aim.
  • Aim Line draws a line from the screen centre to the current target, and the FOV ring shows the FOV radius.

10. After a game update

Run the dumper in the shooting range first (§2). If every step passes, the internal picks up the new cfg by itself and there's usually nothing else to do. Skeletons need nothing, since everything in §6 is found at runtime. The overlay needs nothing either, it doesn't use any game data. If it doesn't show up, check R6 is running borderless or windowed.

11. Traps that cost real time

  • Old copies and stale addresses. Palettes move every tick, never cache one.
  • Pooled objects keep their vtable when they're reused, so a vtable check doesn't prove it's the same object. Gate motion on a plausible speed.
  • The u16 "type id" right before an object is just the allocator's chunk header.
  • Check how often the source actually updates before optimising anything downstream (the 3.3 Hz field).
  • History has to advance on change, not on a clock.
  • A one-frame decision (retiring a link, locking a template) needs a rate or sustained evidence, not one sample. The 3 cm one-instant lock rule proved it again in a 10-player scene (§6.5).
  • "First match wins" is not "best match wins". NearFeet handed one player's points to a neighbour for months because the range never put two bodies close together.
  • Ranking candidates and only looking at the top N loses the right one.
  • Before trusting "nothing moved", confirm something could move.
  • GetAsyncKeyState(k) & 1 gets consumed by the first reader. Use the high bit.
  • Standing-only tests (taller than 0.9 m and so on) silently drop prone bodies.
  • Anything started only in the external's render loop never runs in the DLL. The triggerbot thread, config autosave and a debug hotkey all sat dead there. Per-frame work goes in GameOverlay::OnFrame.
  • A watchdog that stops the overlay for good on a 3 s frame stall kills the menu and ESP on every map load and alt-tab. Pause and resume instead.
  • No COM from the DLL (CoCreateInstance, WIC, WinRT). The shim engine in apphelp.dll looks up the caller's loader entry, a manually mapped DLL doesn't have one, and R6 dies.
  • DX11: build the font atlas before the first frame. Rebuilt mid-frame, the old font texture is freed while that frame's draw lists still point at it.
  • Anything polling a list the game rewrites every frame (1 ms poll vs a 7 ms frame) sees it empty or half-written. The archived triggerbot shot through walls that way. Confirm across frames, and re-read the size after the data.
